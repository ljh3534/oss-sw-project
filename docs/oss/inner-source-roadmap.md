# Inner Source 도입 로드맵

> 6주차 선택과제 — 오픈소스 개발 방식(공개 저장소, PR 기반 기여, 비동기 협업)을 **조직 내부**에 적용하기 위한 단계별 계획.
> 가상의 적용 대상: 광고 대행사 "가상 마케팅랩"(개발팀 3개, 약 25명)이 AdPrice 계산 모듈을 사내 견적 시스템의 공용 컴포넌트로 사용하는 상황.

## 1. 왜 Inner Source인가 — 현재 문제

| 문제 | 증상 |
|---|---|
| 사일로 | 팀마다 단가 계산 엑셀·스크립트를 따로 만들어 결과가 제각각 |
| 병목 | 공용 모듈을 고치려면 담당 팀에 요청 후 대기 (평균 2주) |
| 지식 단절 | 계수가 왜 그 값인지 아는 사람이 퇴사하면 근거가 사라짐 |
| 중복 투자 | 비슷한 기능을 3개 팀이 각자 구현 |

## 2. 목표 (12개월)

- 단가 계산 로직을 **하나의 사내 공용 저장소**로 통합
- 다른 팀의 PR(외부 기여) 비율 **30% 이상**
- 공용 모듈 변경 요청의 리드타임 **2주 → 3일**
- 모든 계수 변경은 **ADR + RFC**로 근거를 남김

## 3. 역할 정의

| 역할 | 책임 |
|---|---|
| **Host Team** (소유 팀) | 저장소 운영, 로드맵, 최종 병합 결정 |
| **Trusted Committer** | Host 팀 소속 시니어. 외부 기여자 멘토링, 리뷰 SLA 준수, 기여 가이드 유지 |
| **Contributor** (Guest) | 다른 팀 개발자. 자기 팀에 필요한 기능을 직접 PR로 기여 |
| **Inner Source PMO** | 지표 수집, 교육, 인센티브 설계 |

## 4. 단계별 로드맵

| 단계 | 기간 | 핵심 활동 | 산출물 | 완료 기준 |
|---|---|---|---|---|
| **0. 준비** | 1개월 | 경영진 후원 확보, 파일럿 저장소 선정(AdPrice 계산 모듈), Trusted Committer 2명 지정 | 도입 제안서, 파일럿 범위 | 후원자·TC 확정 |
| **1. 기반 구축** | 2개월 | 사내 GitHub Enterprise 저장소를 *사내 전체 공개(internal)* 로 전환, README·CONTRIBUTING·CODEOWNERS·PR 템플릿·리뷰 가이드 정비, CI 필수화 | 기여 가능한 저장소 | 신규 입사자가 문서만 보고 첫 PR 가능 |
| **2. 파일럿** | 3개월 | 다른 2개 팀에서 Contributor 지정, `good first issue` 10개 공개, 주간 오피스아워, Discussions로 비동기 Q&A | 외부 PR 10건+ | 외부 기여 PR 병합 10건, 리뷰 응답 SLA 24h 준수율 80% |
| **3. 확산** | 4개월 | 사내 공용 컴포넌트 3개로 확대, Inner Source 포털(저장소 카탈로그) 구축, 기여를 인사평가에 반영 | 카탈로그, 평가 기준 | 공용 저장소 4개, 기여 팀 5개 이상 |
| **4. 정착** | 지속 | 지표 대시보드, 분기 회고, 우수 기여자 시상, ADR/RFC 문화 정착 | 분기 리포트 | 아래 KPI 달성 |

## 5. 운영 규칙 (이 저장소의 관행을 그대로 이식)

| 관행 | 이 저장소 구현 | 사내 적용 |
|---|---|---|
| 기여 가이드 | `CONTRIBUTING.md` | 동일 템플릿 + 사내 보안 규정 링크 |
| 리뷰 태그 | `[MUST]/[SHOULD]` ([리뷰 가이드](../REVIEW_GUIDE.md)) | 동일 — 팀 간 리뷰의 감정 소모 감소 |
| 코드 소유권 | `.github/CODEOWNERS` | Trusted Committer를 경로별 지정 |
| 의사결정 기록 | `docs/adr/` | 계수·아키텍처 변경 시 필수 |
| 비동기 토론 | GitHub Discussions (RFC) | 회의 대신 RFC로 합의 |
| 품질 게이트 | GitHub Actions CI + 브랜치 보호 | 동일 |
| SLA | `sla-tracker.yml` | 리뷰 첫 응답 24h, 완료 48h |

## 6. 측정 지표 (KPI)

| 지표 | 측정 방법 | 목표 |
|---|---|---|
| 외부 기여 비율 | (Host 팀 외 작성자 PR 수) / 전체 PR 수 | 30%+ |
| PR 리드타임 | PR 생성 → 병합 (기존 `metrics.yml` 확장) | 중앙값 3일 이하 |
| 리뷰 첫 응답 시간 | PR 생성 → 첫 리뷰 | 중앙값 24h 이하 |
| 재사용 팀 수 | 공용 모듈을 의존성으로 쓰는 서비스 수 | 5개+ |
| 중복 구현 제거 | 폐기된 사내 중복 모듈 수 | 3개+ |

## 7. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| Host 팀 리뷰 부담 증가 | Trusted Committer 시간 20%를 공식 업무로 배정, 자동화(CI·린트)로 기계적 리뷰 제거 |
| "남의 코드 고치기" 문화적 거부감 | 경영진 메시지 + 기여를 평가에 반영, 첫 기여자 멘토링 |
| 품질 저하 | 브랜치 보호 + 필수 CI + CODEOWNERS 리뷰 |
| 보안·기밀 노출 | 사내 전체 공개 범위만 허용, 비밀값은 Secrets로만, 시크릿 스캐닝 활성화 |
| 일회성 이벤트로 끝남 | 분기 지표 리뷰를 PMO 정례 업무로 고정 |
