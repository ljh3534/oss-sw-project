# 코드 리뷰 가이드

> 목적: 버그를 일찍 잡고, 지식을 공유하고, 일관된 품질을 유지한다. 사람을 평가하는 자리가 아니다.

## 1. 리뷰 코멘트 태그

모든 코멘트는 아래 태그 중 하나로 시작한다. 태그만 보고도 "병합을 막는 코멘트인지"를 알 수 있게 하기 위함이다.

| 태그 | 언제 쓰나 | 작성자 대응 |
|---|---|---|
| `[MUST]` | 버그, 보안 문제, 요구사항(PRD) 위반, 테스트 누락, CI 실패 원인 | 반드시 수정 후 재요청 |
| `[SHOULD]` | 가독성·유지보수성·성능상 강하게 권장 | 수정하거나, 하지 않는 이유를 답글로 |
| `[COULD]` | 더 나은 대안 제안 (선택) | 자유 |
| `[NIT]` | 오타, 사소한 스타일 | 자유 |
| `[QUESTION]` | 의도 확인 | 답변 |
| `[PRAISE]` | 좋은 코드·아이디어 칭찬 | — |

### 좋은 코멘트의 구조

```
[MUST] 팔로워 수가 0이면 참여율 계산에서 0으로 나누기가 발생합니다.
- 근거: PRD 8장 "팔로워 0명 방지" 요구사항
- 제안: validateInput()에서 followerCount < 1000 이면 에러를 던지도록
```

**태그 → 문제 → 근거 → 제안** 순서로 쓴다.

## 2. 리뷰 체크리스트

### 기능
- [ ] PR 설명과 실제 변경이 일치하는가?
- [ ] PRD의 계산 공식·계수와 일치하는가?
- [ ] 경계값(구간 경계, 0, 음수, 매우 큰 수)을 처리하는가?

### 테스트
- [ ] 새 로직에 단위 테스트가 있는가?
- [ ] CI(Lint/Test/Build)가 통과하는가?

### 코드 품질
- [ ] 계수가 하드코딩되지 않고 `coefficients.json`에서 오는가?
- [ ] 함수가 한 가지 일만 하는가? 이름이 의도를 드러내는가?

### 보안 / 운영
- [ ] 비밀값이 코드·로그에 노출되지 않는가? (Secrets 사용)
- [ ] 워크플로 권한(`permissions`)이 최소한인가?

### 문서
- [ ] README / Wiki / ADR 갱신이 필요한 변경인가?

## 3. 리뷰 프로세스와 SLA

| 항목 | 기준 |
|---|---|
| 첫 응답 | PR 생성 후 **24시간 이내** |
| 리뷰 완료 | **48시간 이내** (SLA 추적 워크플로가 초과 시 `sla-breached` 라벨 부착) |
| 승인 조건 | CI 통과 + 미해결 `[MUST]` 0건 |
| 병합 방식 | Squash merge, 병합 후 브랜치 삭제 |

## 4. 작성자를 위한 셀프 체크
- PR은 하나의 목적만 담는다 (400줄 이하 권장).
- 리뷰 요청 전에 직접 diff를 한 번 읽는다.
- 코멘트에는 모두 답글을 단다. 반영했다면 반영 커밋 해시를 남긴다.
