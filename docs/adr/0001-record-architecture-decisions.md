# ADR-0001: ADR로 아키텍처 결정을 기록한다

- **상태**: Accepted
- **날짜**: 2026-11-13
- **결정자**: @ljh3534
- **관련**: #8

## 배경
학기 프로젝트는 16주 동안 진행되고 이후 오픈소스 기여자를 모집할 계획이다(PROPOSAL 2학기 계획). 결정 이유가 PR 댓글·메신저에 흩어지면 새 기여자는 맥락을 알 수 없다.

## 검토한 대안
| 대안 | 장점 | 단점 |
|---|---|---|
| A. 기록하지 않음 | 비용 없음 | 같은 논의 반복, 근거 소실 |
| B. Wiki에 기록 | 편집 쉬움 | 코드와 버전이 분리되고 리뷰를 거치지 않음 |
| C. 저장소 `docs/adr/`에 Markdown ADR | 코드와 함께 버전 관리, PR 리뷰로 합의 | 작성 습관이 필요 |

## 결정
Michael Nygard 형식을 단순화한 ADR을 `docs/adr/`에 Markdown으로 기록하고, PR 리뷰를 거쳐 `Accepted`로 만든다.

## 결과
- 좋아지는 점: 결정 근거가 git 이력과 함께 남는다. 리뷰에서 ADR 링크로 반복 논의를 줄인다.
- 감수할 점: 결정마다 문서 작성 비용.
- 후속 작업: CONTRIBUTING·리뷰 가이드에 ADR 작성 기준 링크.

## 재검토 조건
ADR이 3개월간 한 건도 추가되지 않으면 기준이 너무 엄격한지 검토한다.
